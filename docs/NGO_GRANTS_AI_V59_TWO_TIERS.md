# NGO Grants AI v5.9 — дві категорії відповідності (прототип)

Статус: **ізольована гілка, не розгорнуто**. Поточні v5.7/v5.8 і повідомлення першого замовлення не змінені. Додано preview-інтеграцію, яка працює лише для `dry_run=True` за явного `NGO_GRANTS_V59_PREVIEW=1`.

## Контракт

- **Пряма відповідність:** підтверджені фінансована діяльність, заявник, цільова група, географія та чинний прийом.
- **Умовна відповідність:** фінансування саме запитаної діяльності, географія й чинний прийом підтверджені, але існує конкретна перевірна умова щодо заявника, бенефіціарів або іншого обмеження. Умовний результат завжди містить причину й перелік перевірок.
- **Відхилено:** дедлайн минув / не доведено постійний прийом / географія не підтверджена / запитана діяльність не фінансується / вимога лише проєктного фінансування не виконана / категорія заявника виключена.

## Безпечна інтеграція

1. Після визначення дедлайну, географії, фінансованої діяльності та типу фінансування викликати `decide_match` із доказовими булевими значеннями; не виводити їх тільки з назви програми.
2. Після моделі повторно застосовувати незалежні жорсткі критерії. Модель не може підвищити reject до conditional.
3. Генерувати **основний PDF лише з direct**. Умовні можливості формувати **окремим додатком**, кожну — з причиною, необхідною перевіркою та джерелом; не змішувати з підтвердженими грантами.
4. Якщо direct=0, не писати «взагалі немає можливостей», коли є conditional: окремо вказувати, що прямі не знайдені, а суміжні потребують перевірки.
5. Зберегти дедлайн-фільтр незалежним для кожного рівня; уникати повторного відправлення завершеного першого замовлення.
6. Перед злиттям провести інтеграційні тести PDF, Telegram та перевірку архіву на контрольному замовленні без публікації.

## Обмеження прототипу

`catalog_tiers_v59.py` — окремий детермінований класифікатор з тестами. Він **не підключений до продуктивного потоку** і не виконує сам пошук грантів, перевірку донорських сторінок або відправлення в Telegram. Це дозволяє перевірити правила без ризику для реальних замовлень.

## Зроблено для безпечного preview

- Модуль `catalog_presentation_v59.py` розділяє вже перевірені рядки на прямі й умовні, ще раз відсікаючи минулі/непідтверджені дедлайни й відхилені типи заявника.
- У `ngo_grants_ai.py` додано **лише opt-in гілку**: `dry_run=True` разом із `NGO_GRANTS_V59_PREVIEW=1` створює два окремі PDF, якщо є матеріал для кожної категорії. Публікації немає.
- Умовні картки зберігають пояснення `_conditional_reason` у полі застережень.
- Додано тести на відсутність прямих грантів, повтори, минулі дедлайни, непідтверджений постійний прийом та відхилення заявника.

**Важливо:** цей preview не є випуском у production: єдиний продуктивний шлях відправлення залишається старим. Підготовку двох документів слід протестувати за безпечного стану черги або на синтетичному замовленні, не змінюючи реальну чергу.

## Перевірки в гілці

- `tests/test_catalog_tiers_v59.py`: 10 граничних ситуацій для первинної класифікації.
- `tests/test_catalog_presentation_v59.py`: розділення категорій і повторна перевірка дедлайнів.
- `tests/test_catalog_v59_pdf_preview.py`: обидва PDF дійсно створюються та містять тільки власні картки; перевірка PDF здійснюється через `pypdf`.
- `tests/test_catalog_v59_preview_safety.py`: мокований preview запускає весь шлях до PDF і перевіряє відсутність викликів Telegram, збереження стану і зміни черги.
- Preview використовує глибоку копію стану та не виконує `save_state`.

Усі перевірки виконуються через існуючий CI GitHub у Pull Request. **Merge та production deployment свідомо відкладено до окремої інтеграції безпечної доставки двох документів.**

## Журнал доставки та захист від дублювання

Підготовлено `ngo_grants_v59_delivery.py`: маніфест замовлення, стан кожного документа `prepared → sending → sent`, ідентифікатор Telegram-повідомлення та відбиток складу грантів. Якщо відповідь Telegram втрачено після спроби надсилання, запис залишається у `sending`. Система **не надсилає повторно автоматично**, щоб уникнути дубля; оператор повинен звірити публікацію та підтвердити конкретний message_id через `reconcile_document`.

Підготовлено `ngo_grants_v59_checkpoint.py`: перед кожною спробою надсилання і після отримання підтвердження з Telegram стан негайно комітиться та синхронно відправляється в `origin/main`; перевіряється SHA віддаленої гілки. Якщо GitHub не підтвердив запис, зовнішня відправка не виконується. Це потрібно, тому що стандартний workflow комітить локальний стан лише **після** завершення Python-процесу, а цього недостатньо для захисту від повтору після падіння runner.

**УВАГА:** код інтеграції розташований тільки в тестовій гілці. Активується виключно за `NGO_GRANTS_V59_LIVE_DELIVERY=true` та середовища GitHub Actions; робочий workflow цю змінну наразі **не передає**. Жодна реальна публікація v5.9 не проводилася. До релізу необхідні контрольні перевірки і ручний план відновлення зі стану `sending`.

## Перевірки без публікації

- `tests/test_ngo_grants_v59_delivery.py`: повторні спроби, невизначений мережевий результат, часткове надсилання, ручна звірка.
- `tests/test_ngo_grants_v59_checkpoint.py`: відмова GitHub push, помилкова гілка, відмінність remote SHA.
- `tests/test_ngo_grants_v59_integration.py`: повний замокований шлях із двома документами та непорушністю черги до їхньої доставки.

## Обмеження

Telegram Bot API не забезпечує вбудованого idempotency key для `sendDocument`. Тому за невизначеної відповіді потрібне втручання оператора. Після merge потрібно перевірити реальний Git push на staging без Telegram і синхронізацію Cloudflare Worker. Наявність зеленої unit-CI не є підтвердженням продуктивного релізу.

## Staging-збірка без секретів

- `scripts/v59_staging_preview.py` формує два PDF на **вигаданих** прикладах і підтверджує, що прострочена програма не з'явилася в жодному з них.
- `.github/workflows/ngo-grants-v57-ci.yml` запускає цей генератор при Pull Request та зберігає артефакт `ngo-grants-v59-synthetic-two-tiers` на 7 днів.
- Навігація `show_catalogs` показує обидва Telegram-посилання з правильним типом файлу, а для старих каталогів залишає одне посилання.
- Добовий ліміт у `can_publish` враховує кількість PDF-документів, не лише кількість замовлень.
- Основний GitHub workflow тримає `NGO_GRANTS_V59_LIVE_DELIVERY: 'false'` жорстко вимкненим. Репозиторні змінні не можуть випадково активувати нову доставку. Увімкнення можливе лише через окрему зміну коду після завершення release-acceptance тестів.

Ці staging PDF не є справжніми каталогами і не мають надсилатися в канал. Результат тестування стає достовірним після зеленого GitHub CI для відповідного commit SHA.

## Відновлення після невизначеної доставки

Оператор **спочатку вручну перевіряє в каналі**, чи з'явився конкретний PDF. Якщо так, у GitHub Actions → `NGO Grants — AI catalogs` → `Run workflow` заповнюються **одночасно** три поля: `v59_reconcile_order` (ID замовлення), `v59_reconcile_tier` (`direct` або `conditional`) і `v59_reconcile_message` (перевірений Telegram message_id). Ця дія запускає лише `--v59-reconcile-*`, підтверджує запис через durable checkpoint і **не надсилає нічого в Telegram**. При невпевненості в message_id підтвердження робити не можна: потрібне ручне розслідування. Автоматичного повторного надсилання для `sending` немає.

За відсутності повідомлення в каналі **не треба** вигадувати message_id: питання вирішується окремою адміністративною процедурою, поза автоматичним retry.

## Реальний Git subprocess test без production

Додано `tests/test_ngo_grants_v59_real_git_checkpoint.py`: CI створює локальний bare-репозиторій, окрему `main` і перевіряє справжню послідовність git commit → pull --rebase → push → порівняння remote SHA. Тест не має доступу до реального GitHub main і не надсилає нічого в Telegram. Підтверджене проходження: `42385965089`.

На час підготовки цього документа релізна гілка все ще відокремлена від `main`; лише автоматизоване локальне моделювання Git не замінює реального end-to-end підтвердження Cloudflare + Telegram.

## Безпечний code-only dark launch

Для підготовки до злиття з `main` параметр `NGO_GRANTS_V59_LIVE_DELIVERY` **жорстко встановлено в `false`** у scheduled workflow. Це гарантує, що навіть випадково створена GitHub repository variable не ввімкне нову схему відправлення. Реальні замовлення продовжують оброблятися попереднім шляхом v5.7/v5.8. Будь-яка активація v5.9 потребує окремого Pull Request із перевіркою Cloudflare sync та операційного recovery.

Додатковий захист: після відправлення першого файлу система зберігає самі PDF у Git, а не лише шляхи до них. Наступний runner може без ШІ прочитати frozen manifest та відправити лише непідтверджені документи; їхні SHA-256 і дедлайни перевіряються перед продовженням. Якщо стан `sending` невизначений, відправлення призупиняється до ручної звірки. Уже підтверджена повна доставка може бути записана в журнал навіть після досягнення денного ліміту, без нових Telegram-повідомлень.
