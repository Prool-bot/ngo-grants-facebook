# NGO Grants AI — перевірка повного циклу Mini App v0.2

Дата: 7 листопада 2026 року. Область: робоча Telegram Mini App, Cloudflare Worker, D1-черга та GitHub Actions NGO Grants AI v5.9.

## Що ця перевірка робить автоматично

1. Зчитує `GET /health` та HTML `GET /mini-app` з робочого Cloudflare Worker (перевірка v0.2, 7-крокової анкети, видимої «Продовжити» на кроках 6/7 та 7/7).
2. Зі службовими секретами робить **лише GET** `/internal/pending` та показує **тільки кількість** очікуваних заявок. Не розкриває теми, контактні дані, внутрішні ID, часові позначки.
3. Перевіряє, що повністю активна саме затверджена Worker-версія v0.2, усі 5 bindings збережені. Зчитує приватний Worker у тимчасову пам'ять GitHub runner.
4. У **пам'яті ізольованого Node.js** замінює лише виконання `createRequest` на **безпечний лічильник викликів**. Не змінює сервер. Виконує автентичний обробник `handleTelegram`, передаючи синтетичне `message.web_app_data` (як це робить Telegram `KeyboardButton`). Перевіряє аргументи: `chatId`, `userId`, `updateId`, усі `facets`, `stage=confirm`. Реальний `validatedDraft` повинен прийняти цей запит.
5. Імітує шахрайський user ID і недопустимі напрями. У цих випадках `createRequest` **не повинен викликатися**, а Telegram-відповідь перехоплюється фальшивим `fetch`.
6. Проганяє регресію попереднього Worker v5.8, UI-тести, окремі модулі v5.9.
7. Створює **синтетичні PDF** у каталозі runner, без публікації в Telegram. Для технічного перегляду PDF доступні як artifact на сторінці тестового GitHub Actions run.

## Чого ця перевірка свідомо НЕ робить

- Не створює **реального** замовлення від Telegram-користувача.
- Не намагається підробити Telegram webhook або impersonate user's account.
- Не надсилає повідомлень від імені бота, не торкається D1-записів, не застосовує квоту на день.
- Не публікує PDF у `@ngo_grants`.
- Не переписує Worker, webhook, workflow планування або наявні обмеження.

## Як завершити справжній E2E

Справжній ланцюжок **Telegram Mini App → підтверджений Telegram update → Cloudflare D1 → GitHub scheduled run → канал/каталог** потребує хоча б одного **реального** натискання «Замовити каталог» у Telegram, зробленого користувачем. Автоматизовані тести не замінюють цього доказу. Після цього потрібно переконатися, що створено **тільки 1** D1-запит, він отримав статус обробки, потрапив у GitHub-чергу і отримав підтверджену публікацію або повідомлення про відсутність результатів (без вигаданих посилань чи часів). Лише після такого доказу позначати повний цикл підтвердженим.

Результати live read-only acceptance: `.github/workflows/mini-app-e2e-readonly.yml`.
