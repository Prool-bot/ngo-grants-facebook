# NGO Grants AI — Mini App / Mascot UI (v0.1)

**Статус:** автономна інтерактивна демонстрація. **НЕ надсилає** замовлень, не публікує PDF, не змінює Cloudflare Worker, Telegram webhook, GitHub state або діючий бот.

## Що готово

- Затверджений світлий робот з темно-синім обличчям, без антени, смуг на плечах і декоративних рисочок над руками. Файл `assets/mascot.svg` містить компактну копію затвердженого графічного образу (вбудоване оптимізоване WEBP-зображення).
- Компактний адаптивний екран: робот розташований поруч із запитанням, блок залишається видимим на мобільних пристроях.
- Спокійна поведінка: немає безперервного махання. Реакція лише на натискання відповіді, повернення або перезапуск; підтримка reduced motion.
- Форми з реальними кодами параметрів **наявного** Worker / Python: `audience`, `sectors[]`, `custom_sector`, `geo`, `region`, `detail`, `applicant_role`, `funding_format`.
- Кілька незалежних секторів, окремий вибір регіону, уточнення діяльності, перевірка перед підтвердженням.
- На останньому екрані є чітке повідомлення: **прототип не надсилає реального замовлення**.

## Як відкрити

Найпростіше: завантажити **`mini-app/preview.html`** і відкрити подвійним натисканням у браузері. Це один автономний HTML-файл із вбудованими стилями, скриптами та затвердженим зображенням робота. Для розробки також можна відкрити `mini-app/index.html` (модульна версія з окремими файлами). Усі CSS/JS/зображення — локальні файли без сторонніх бібліотек і платних API. GitHub Actions зберігає ZIP із попереднім переглядом у workflow artifact `mini-app-static-preview`.

## Контракт передачі даних

Після заповнення форми викликається `NgoGrantsSchema.normalize(draft)`. Його результат має лише:

```json
{
  "audience": "nonprofit",
  "sectors": ["social", "recovery"],
  "custom_sector": "",
  "geo": "region",
  "region": "kharkiv",
  "detail": "Соціальний транспорт",
  "applicant_role": "lead",
  "funding_format": "grant_only"
}
```

Це **не авторизація**. Не дозволяти `sendData` напряму створювати запис у черзі та не довіряти жодному `user_id` із браузера.

## Наступний безпечний етап: інтеграція

Створити вузький server-side endpoint для замовлення в чинному Cloudflare Worker. Перш ніж активувати публічний UI:

1. Перевірити Telegram WebApp **`initData` серверним HMAC-SHA256** (врахувати правильний Mini App validation алгоритм для Bot Token), TTL та наявність користувача; не довіряти `initDataUnsafe`.
2. На сервері повторно валідувати весь `facets` payload, підписку на `@ngo_grants`, денний ліміт 1 запит/особу та правила черги.
3. Підтвердження замовлення повинно бути **idempotent**: захист від подвійного тапу й повторного HTTP-запиту до commit.
4. Тільки після атомарного серверного підтвердження відповідати успіхом; у разі помилки відновлювати форму без втрати введених користувачем параметрів.
5. Підтвердити сумісність із поточною схемою Cloudflare D1, не створювати другого паралельного планувальника пошуку.
6. Створити окремий guarded rollout для кнопки Mini App у робочому боті, із можливістю миттєвого відкату. Поки не змінювати продакшн.

**Принцип:** Mini App — лише інтерфейс чинної NGO Grants AI системи; грантові каталоги обробляє наявний бекенд.

## Серверна перевірка Telegram initData — підготовлений модуль

Для наступної інтеграції створено `worker/mini_app_verify_init_data.mjs`. Модуль використовує Web Crypto API Cloudflare Worker і **не підключений до робочого HTTP-маршруту**. Він перевіряє HMAC-SHA256 за [офіційним алгоритмом Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), `auth_date`, дублікати параметрів і коректний ID користувача. Повертає тільки підтверджений ID та часову позначку, не виводить в журнали токени або приватні дані. Тестовий вектор із документації Telegram і перевірки на підміну, прострочення, дублювання та майбутні дати покриті `mini-app/tests/auth.test.mjs`.

Це **не означає**, що користувацькі замовлення уже можна подавати з Mini App. Інтеграція до чинної черги та серверна перевірка підписки/денного ліміту залишаються наступною роботою.

## Підготовлений контракт серверного замовлення (поки неактивний)

`worker/mini_app_order_endpoint.mjs` — модуль для майбутнього маршруту `POST /api/mini-app/order`. Він **не доданий до чинного Worker**. Приймає мінімальний JSON із `initData` Telegram, валідованими `facets` і випадковим UUID v4 `idempotencyKey`. Відхиляє сторонні поля (особливо `user_id`/`chat_id`), перевіряє підписаний Telegram User ID, строк чинності `initData`, допустимі значення та розмір запиту. Не записує жодної заявки самостійно.

Після перевірки викликає **обов'язково реальний** `deps.enqueueExistingOrder({userId,facets,idempotencyKey})`. Цей адаптер ще не реалізовано: він повинен атомарно перевірити членство в каналі та денну квоту за правилами **чинного Worker**, використати існуючу D1-чергу й повертати лише підтверджений DB-commit (`created` або `existing` з `orderId`). Модуль за замовчуванням не працює: вимагає явного `MINI_APP_ORDER_ENABLED="true"` у Worker та встановленого адаптера. Якщо адаптера або підтвердження commit немає, повертає HTTP 503, **не видає фальшиву відповідь про замовлення**.

Негативні відповіді: 400 — хибний payload, 401 — Telegram auth, 403 — відсутність підписки або заборонене джерело, 409 — конфлікт, 413 — завеликий запит, 429 — денний ліміт, 503 — сервіс вимкнений/результат commit не підтверджений. Повтор із тим самим ключем повинен повернути `existing` для того самого замовлення.

Тестування: `node --test mini-app/tests/*.test.mjs`. Скрипт `scripts/mini_app_worker_shape_audit.py` читає актуальний Worker **тільки у пам'яті GitHub runner**, виводить лише структурні ознаки та назви релевантних функцій, не публікує вихідний код. Аудит потрібен, щоб адаптуватися до фактичної структури існуючої D1-черги, а не вигадувати нові таблиці.

**Важливо:** робочий Telegram-бот і Cloudflare Worker на цьому етапі не змінені.

## Спрощена інтеграція через штатний Telegram KeyboardButton (v0.2, staging)

Після перевірки [офіційної документації Telegram Mini Apps](https://core.telegram.org/bots/webapps) обрано **простіший шлях без окремого публічного REST API**. Mini App, відкритий **саме з reply-keyboard кнопки** `web_app`, має штатний метод `Telegram.WebApp.sendData(payload)`. Telegram перетворює його на серверне повідомлення `message.web_app_data`, яке отримує **наявний** Cloudflare Worker через захищений webhook. Цей метод не працює при відкритті Mini App із меню/inline-кнопки, тому пропонуємо команду `/assistant`, яка надсилає reply-клавіатуру з кнопкою `🤖 Відкрити грантового помічника`. Кнопка `/start` повертає до звичайного бота.

Новий модуль `worker/mini_app_keyboard_bridge.mjs` перевіряє `message.from.id === message.chat.id` для приватного чату, тип `web_app_data`, маркер схеми `ngo-grants-miniapp-v1` та усі `facets` — **ніколи не довіряє ID, надісланому HTML-формою**. Для створення замовлення викликає **той самий** `createRequest(env, chat, userId, draft, updateId)` із чинного Worker, де вже діють `getChatMember`, перевірка попереднього замовлення, денні ліміти та атомарна робота з D1. Підтвердження заявнику надсилає основний бот, а не браузер. Жодного дублювання пошукової логіки немає.

`worker/patch_live_worker_mini_app.py` у пам'яті GitHub Actions runner вставляє до чинного v5.8 Worker тільки маршрут `GET /mini-app`, обробку `/assistant` та `web_app_data`. Для цього використовує перевірені точні anchors та відхиляє невідомий Worker. Публічний файл `preview.html` **лишається з `data-native-send="false"`**. У Worker-версії ця опція вмикається під час staging разом з офіційним Telegram JS SDK.

`.github/workflows/mini-app-stage.yml` — **лише створення неактивної Cloudflare Worker version** із суворим успадкуванням чинних DB/AI/secret bindings. Не перемикає трафік, не відправляє повідомлень Telegram, не змінює webhook або робочу D1-чергу. Перед майбутнім перемиканням треба перевірити незалежний staged Worker та реальну роботу `createRequest` через webhook. Після успішної перевірки можливо додати `/assistant` до меню команд бота.

**Відмінність від підготовленого REST endpoint:** `worker/mini_app_order_endpoint.mjs` залишається неактивною альтернативою. У новому шляху Mini App не отримує Telegram bot token і не виконує API-запити до D1. Для штатного `sendData` не потрібний `initData` HMAC, оскільки підтвердження особи йде з Telegram webhook update. Серверний HMAC-модуль збережено для можливого іншого способу запуску в майбутньому.

## Підготовка прямого запуску із каналу (новий, поки НЕАКТИВНИЙ модуль)

Додано `mini-app/direct-client.js` та перевірки `mini-app/tests/direct-client.test.cjs`. Це фундамент для майбутнього Main/Direct Mini App, який відкриватиметься **поверх `@ngo_grants`** без переходу до розмови з ботом.

Модуль **не завантажується жодною робочою HTML-сторінкою** та за замовчуванням відхиляє надсилання. Він уміє приймати сирий підписаний `Telegram.WebApp.initData` і канонічні `facets`, створює один UUID v4 на спробу замовлення й використовує його повторно після технічних збоїв. Модуль надсилає тільки HTTPS POST на той самий origin `/api/mini-app/order` та визнає успіхом **лише HTTP 200/201 з підтвердженим `order_id` після серверного commit**. Він ніколи не використовує `initDataUnsafe` або ID, заявлений клієнтом, і не підміняє відповіді сервера.

Поки немає реального чинного Worker-адаптера до наявної D1-черги та підтвердженої конфігурації Main Mini App через BotFather, **не вмикати `enabled=true`** і не використовувати посилання `?startapp` як заміну чинній кнопці в каналі. Сервер має перевіряти Telegram HMAC, підписку, денний ліміт у Києві та повторні замовлення; у разі відсутності можливості написати користувачу в особистий чат підтвердження слід показувати в самому Mini App.

Повний план та критерії готовності — GitHub Issue #34. Поточний продакшн залишається v0.4 на режимі клавіатури бота.

## Direct-from-channel UI — безпечна підготовка (2026-11-08)

Додано автономний **`mini-app/direct-preview.html`** із повним 7-кроковим інтерфейсом і модулем `direct-client.js`. Це **offline preview**: `data-native-send="false"`, `data-direct-send="false"`. Він не відправляє заявки і не створює фальшивих підтверджень.

У `app.js` реалізована окрема гілка `data-direct-send="true"`, що може бути активована **лише під час майбутнього контрольованого серверного розгортання**. Вона вимагає підписаний Telegram `initData`, WebCrypto UUID, same-origin HTTPS і серверний endpoint. Якщо клієнт не має перевіреного Telegram-сеансу, кнопка замовлення заблокована. Після натискання відображається номер замовлення **лише після** статусу HTTP 200/201 та підтвердженого D1 commit. Якщо сервер недоступний, форма не стирається, повідомляється про помилку, можна повторити з тим самим ідемпотентним ключем.

Наявний `data-native-send="true"` із `Telegram.WebApp.sendData` **залишається окремим робочим шляхом** для клавіатури бота. Одночасне ввімкнення двох режимів — помилка конфігурації. Середовище production наразі лишається v0.4; жодна з підготовлених direct-сторінок не зареєстрована у Cloudflare або BotFather.

Перевірки `mini-app/tests/flow.test.cjs` і `mini-app/tests/direct-client.test.cjs` перевіряють успішний серверний receipt, заборону фальшивого повідомлення, відхилення 503, збереження можливості повтору та незмінність старого інтерфейсу.
